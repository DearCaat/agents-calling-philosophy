# 执行者：脚本、判定模型、直接调用 API、harness

一件活可以交给四类执行者。它们的能力、成本和出错方式各不相同，按任务需要选；先定下模型或 harness 再给它找活，等于让工具决定任务。本机入口：判定模型与 API 见 `local/apis.md`（直接调用，不经 `dispatch.sh`）；harness 见 [SKILL.md](../SKILL.md) 的派工程序与 [harnesses.md](harnesses.md)。

## 脚本

做确定性的工作。脚本的结果可复现、可检验，出了错能定位；同样的事交给模型，既贵又会引入随机错误。模型的价值在判断，确定性的部分留给脚本，模型的预算才花在判断上。

## 判定模型

在给定选项里返回概率，不生成文字。

- 只输出概率，所以快、便宜，能大批量跑，适合分类、初筛和当参考信号；概率可以设阈值，也能拿已知答案校准。
- 它不给理由，判错了也没法从输出里看出原因；准不准随任务变化。所以新的用法先拿已知答案校准，关键判断不单靠它。
- 不同模型的概率分布各不相同，阈值不能互相套用。

## 直接调用 LLM API

判断和生成都能做；适合要吃较长上下文、判断较复杂，或判决要附理由供人审查（白盒）的时候。

- 没有 harness 的系统提示和工具循环，输入全是任务本身，开销小，行为也更可控。
- 代价是材料要由调用方备齐，参数没人代设。漏设了参数模型照样回答，只是质量悄悄变了，所以要从回包里核实设置生效。
- 输出上限默认不设，截断要当失败。推理模型的思考能吃掉几万 token，任何默认上限都会截掉一部分答案，截掉一半甚至全空；接口不报错，回包看起来和正常结果一样，混进结果后要到下游才发现。所以脚本两种格式都不发上限，要设由调用方显式给；坚持要上限的接口（如 Anthropic 官方）会直接回 400，这是显式报错，不会静默。结束原因是长度用尽的，判失败，调大或去掉上限重跑。
- 开思考的参数随格式不同：chat 用 `reasoning_effort`，Messages 用 `thinking={"type":"enabled"}`。参数名对不上时通道把它丢掉、不报错，模型就不思考，答案悄悄变差；有的模型在 Messages 下默认不思考，不传就不思考。`budget_tokens` 不写，它是思考的上限，和输出上限一样会截断。Messages 回包通常没有思考 token 数，是否思考看回包里有没有思考内容，脚本结尾会报几条结果有思考。
- 思考偶尔会失控：同一请求多数次正常，个别一次一路想到输出上限、答案为空（本机同一题 8 次里 1 次，`local-test`）。这是那一次的事，不是题目或通道坏了，在原通道重发一次通常就过，脚本默认这样做（`--runaway-retries`）；不要为此换到更慢的通道。流式接收时可用 `--think-limit` 当场截停，不必等满上限。
- 等了几分钟才回来的超时（408、504、524，或等满 `--timeout`）不重发：同一请求还会等满同样的上限（本机一条请求在一个通道上连拿 5 次 504，每次约 9 分钟，共 46 分钟，`local-test`）。脚本默认流式接收，持续收不到数据超过 `--idle-timeout` 才放弃重发；不能流式的通道用 `--no-stream`。
- 长提示批量先冒烟两三批，再按量到的耗时和截断率定每批大小和并发。开思考后单次输出可达数万 token，直接全量时截断和重试会把墙钟拉长数倍（本机一次判分 60 批跑了 2 小时 20 分，`local-test`）。
- 换模型或通道要读图时，先拿一张已知内容的图实测。有的路由把图转成文本或缩到固定尺寸，模型照样回答、不报错，描述是编的（本机一条经 harness 的路由把图变成 base64 文本，`local-test`）；harness 同理。
- 调用用 [scripts/llm-call.py](../scripts/llm-call.py)：两种协议、流式接收、并发、按错误类别重试、逐条落盘和续跑、按缓存口径拆 token 都已做好，截断、回包模型与请求不符、推理参数没生效这类静默问题也会报出来。每次另写一个，这些细节要重做一遍，最容易出错的正是重试、续跑和这些静默问题。

### 让缓存命中

厂商把见过的前缀存下，之后的请求从第一个 token 起逐字比对，对上的部分直接复用。复用的部分不用重算，所以更快；付费通道上只按原价的零头计，免费通道上也少占额度和网关。缓存在厂商一侧，与协议无关，直接调用一样能命中。

- 前缀能一致的就逐字一致。比对从第一个 token 开始，任何一处不同，从那里往后全部落空：多一个时间戳、换一下字段顺序、措辞改一个字，后面几万 token 的缓存就作废。
- 固定的放前面，逐条变化的放最后。指令、评分标准、共享材料每次都一样，放在前面才能被一批请求共用；条目、编号、时间每次都不同，放在前面会让它后面的一切都不命中。
- 共享前缀的请求要落到同一个上游、同一个账号。缓存存在各上游、各账号里，网关把请求分到别处，前缀再一致也落空。请求带上会话标识，网关才能按它粘住上游：脚本默认用 system prompt 的哈希作 `X-Session-ID`，同一批共用一个；多轮任务的共享前缀在 messages 里时，用 `--session-id` 指定。网关认不认这个头见 `local/apis.md`。
- 一批请求先串行发几条再并发。厂商要先见过一个前缀才把它存下，存下还要几秒；同时发出的请求都赶在存下之前，会一起落空。`llm-call.py` 默认这样做。
- 命中多少看回包的 usage，不靠推断。命中不保证，有没有缓存、稳不稳因通道而异：轮换账号的通道时有时无，有的通道根本不缓存。本机各通道的实测见 `local/apis.md`。

## harness

模型自己取材、调用工具、多轮动手；适合输入没法事先备齐、需要探索或改动环境的任务。

- 极简的壳基本只有模型加少量工具；成熟的 harness 有压缩、子代理、沙箱和会话续用。本机各 harness 的厚薄见 [harnesses.md](harnesses.md)。
- 越厚，能自己做完的活越多，长任务也越稳；但系统提示每轮重发，工具循环每一步都有开销，压缩和工具调用本身也会出故障。输入能备齐、一次判断或生成就够的活，用不上这些能力，只剩成本。

## harness 与直接调用怎么比

总 token 数不是成本：不同的 token 价钱和耗时差几十倍，混在一起数会看错。要分开看：

- 全价的部分：未缓存输入和输出。缓存读只按零头计；输出最贵，生成也最慢。
- 缓存命中率：两种方式都能命中，命中率取决于通道和前缀稳不稳，不取决于执行方式。harness 不会因为轮数多就命中得更多；压缩改写了历史、通道换了账号，前缀都会落空。
- 轮数：harness 每一轮是一次完整的模型调用，只能一轮接一轮地跑；直接调用一次结束，批量还能并发。所以墙钟的差距常常比 token 的差距大。
- 失败面：轮数越多，碰上限流、压缩、工具出错的机会越多，这些失败又常常不报错。
- 质量：前面省下的，只有质量相当时才算数。

这几项随任务和通道变化，推理推不准。拿不准用哪种时，用免费通道把同一批任务各跑一份，按上面几项比完再定；实测比推理便宜，也比推理可靠。
